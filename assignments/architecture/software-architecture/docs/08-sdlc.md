# 08. SDLC и ГОСТ Р 59793-2021

## Выбранная модель SDLC

Для marketplace используется **итеративно-инкрементальная модель** с короткими релизными циклами: discovery → design → implementation → verification → release → feedback. Для рискованных интеграций применяется прототипирование до включения в основной инкремент.

## Сопоставление жизненного цикла проекта и ГОСТ Р 59793-2021

| Аспект | Проектный SDLC | ГОСТ-подход | Вывод |
|---|---|---|---|
| Инициация | product vision, scope, ADR | формализованная стадия определения потребностей/требований | смысл совпадает, форма различается |
| Требования | backlog + спецификации + acceptance criteria | формализованные требования и документы | одинаковая цель — управляемая фиксация требований |
| Проектирование | C4/UML/ER, ADR | архитектурное/техническое проектирование | результат сопоставим |
| Реализация | инкременты, pull request, CI | создание/реализация системы | общий этап реализации |
| Проверка | unit/integration/e2e/security tests | верификация/валидация/испытания | общий контроль качества |
| Ввод в действие | staged rollout | ввод в действие/приёмка | одинаковая цель, разная степень формализации |
| Эксплуатация | observability, incidents, SLO | эксплуатационные процессы | общий жизненный цикл после релиза |
| Изменения | continuous delivery | управляемая модификация | в SDLC чаще непрерывно, в ГОСТ формальнее |

## Не менее трёх общих черт

1. **Управление требованиями.** И продуктовый SDLC, и ГОСТ требуют определить ожидаемые свойства системы до приёмки результата.
2. **Проектирование до промышленной эксплуатации.** Архитектура, интерфейсы и данные должны быть описаны до ввода системы в эксплуатацию.
3. **Верификация и валидация.** Оба подхода требуют доказать соответствие решения требованиям через проверки/испытания.
4. **Эксплуатация и сопровождение.** Жизненный цикл не заканчивается разработкой — предусматриваются поддержка и изменения.

## Не менее трёх различий

1. **Степень формализации.** В проектном SDLC часть решений фиксируется ADR, issue и pull request; ГОСТ ориентирован на более формализованный комплект документов. Причина — разные требования к прослеживаемости и приёмке.
2. **Размер итерации.** Marketplace развивается небольшими непрерывными инкрементами; регламентированный процесс легче представить крупными стадиями. Причина — необходимость частого product feedback.
3. **Роль автоматизации.** CI/CD автоматически выполняет сборку, тестирование и часть контроля качества; нормативная модель описывает процессы независимо от конкретного инструмента. Причина — стандарт должен оставаться технологически нейтральным.
4. **Изменение требований.** Agile-подход допускает регулярную реприоритизацию backlog; формализованная схема требует более явного управления изменениями. Причина — стоимость документального согласования.

## Почему выбран итеративный подход

Marketplace имеет несколько независимых областей (каталог, заказы, платежи, доставка, уведомления), поэтому ценность можно выпускать по вертикальным срезам. Формальные артефакты из ГОСТ-подхода используются там, где они повышают прослеживаемость: требования, архитектура, интерфейсы, приёмочные критерии и эксплуатационная документация.
