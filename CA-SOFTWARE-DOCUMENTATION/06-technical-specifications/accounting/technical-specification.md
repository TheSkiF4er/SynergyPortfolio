# Техническое задание — ИС «Бухгалтерия»

Документ подготовлен по структуре технического задания на автоматизированную систему и ориентирован на положения ГОСТ 34.602. Требования сформулированы проверяемым образом, чтобы их можно было использовать при проектировании и приёмочных испытаниях.

## 1. Общие сведения

**Наименование:** ИС «Бухгалтерия».

**Основание разработки:** учебное задание по дисциплине «Документирование программного обеспечения».

**Заказчик:** условная организация — владелец автоматизируемого процесса.  
**Исполнитель:** разработчик информационной системы.

Результатом работ является web-информационная система, документация, схема данных, набор тестов и инструкция по развёртыванию.

## 2. Назначение и цели создания

### 2.1 Назначение
Автоматизация регистрации первичных документов, проводок и формирования учётных отчётов.

### 2.2 Цели
- сократить долю ручных операций и дублирующего ввода;
- обеспечить единый актуальный источник данных;
- снизить число ошибок за счёт валидации и бизнес-правил;
- обеспечить контролируемый доступ и аудит действий;
- сократить время подготовки регламентных и оперативных отчётов.

Критерий достижения: не менее 95% целевых операций должны выполняться в системе без прямого редактирования БД; типовые экранные операции должны завершаться не более чем за 2 секунды при штатной нагрузке.

## 3. Характеристика объекта автоматизации

Автоматизируется подразделение организации, выполняющее процессы: автоматизация регистрации первичных документов, проводок и формирования учётных отчётов. До внедрения допускается использование таблиц, бумажных документов и нескольких несвязанных источников данных. Система должна обеспечить централизованное хранение и формализованный жизненный цикл объектов.

Основные сущности:
- Счёт;
- Контрагент;
- Первичный документ;
- Проводка;
- Учётный период;

## 4. Требования к системе

### 4.1 Требования к системе в целом

#### Архитектура
Трёхуровневая web-архитектура: браузер → HTTP API/приложение → реляционная СУБД. Взаимодействие осуществляется по HTTPS. Развёртывание должно поддерживать отдельные среды development/test/production.

#### Роли
| Роль | Назначение |
| --- | --- |
| Бухгалтер | Работа в пределах выданных полномочий |
| Главный бухгалтер | Работа в пределах выданных полномочий |
| Аудитор | Работа в пределах выданных полномочий |
| Администратор | Работа в пределах выданных полномочий |

#### Надёжность
- подтверждённая операция должна быть атомарной;
- ошибочная операция не должна оставлять частично сохранённые данные;
- резервная копия БД — минимум ежедневно, хранение не менее 14 последних копий;
- целевые RPO ≤ 24 часа, RTO ≤ 4 часа для учебного сценария;
- критичные ошибки приложения журналируются с correlation/request ID.

#### Безопасность
- аутентификация пользователей;
- хранение паролей только как стойких хешей с солью;
- авторизация по ролям;
- защита web-форм от CSRF и входных данных от инъекций;
- TLS для сетевого обмена;
- журналирование входов и критичных изменений;
- принцип минимальных привилегий для БД и системных учётных записей.

#### Производительность
- 95-й перцентиль ответа типового API ≤ 2 с при 50 одновременных пользователях;
- отчёты до 50 000 строк должны формироваться не более 30 с либо асинхронно;
- списки объёмом более 100 записей должны использовать пагинацию.

#### Масштабируемость и сопровождение
Приложение должно поддерживать горизонтальное масштабирование stateless web-узлов; конфигурация хранится в переменных окружения; схема БД изменяется версиями миграций.

### 4.2 Требования к функциям

| ID | Требование | Приоритет |
| --- | --- | --- |
| FR-01 | ведение плана счетов | Обязательное |
| FR-02 | регистрация документов | Обязательное |
| FR-03 | формирование проводок | Обязательное |
| FR-04 | сторнирование | Обязательное |
| FR-05 | закрытие периода | Обязательное |
| FR-06 | формирование оборотно-сальдовой ведомости | Обязательное |

#### Общие правила функций
- обязательные поля валидируются до сохранения;
- сервер повторно проверяет правила независимо от клиентского интерфейса;
- изменение статуса допускается только по разрешённым переходам;
- недоступная пользователю функция не отображается либо возвращает отказ 403;
- удаление значимых данных выполняется безопасно с учётом связей и аудита.

### 4.3 Требования к видам обеспечения

#### Информационное обеспечение
Реляционная БД должна хранить нормализованные сущности и связи. Для ключевых бизнес-объектов применяются уникальные ограничения, внешние ключи и индексы по полям поиска. Экспорт — UTF-8 CSV/XLSX/PDF по назначению.

#### Программное обеспечение
Серверная ОС Linux; актуальная поддерживаемая СУБД PostgreSQL либо MySQL; reverse proxy; web-приложение; современный браузер. Конкретные версии фиксируются в эксплуатационной документации поставки.

#### Техническое обеспечение
Учебная конфигурация: 2 vCPU, 4 GB RAM, 20 GB SSD для приложения и отдельно резервное место. Производственная конфигурация определяется нагрузочным тестированием и объёмом данных.

#### Организационное обеспечение
Назначаются владелец системы, администратор, ответственные за резервирование и пользователи по ролям. Изменение прав выполняется по подтверждённой заявке.

## 6. Порядок контроля и приёмки

Приёмка проводится по функциональным требованиям `FR-*` и нефункциональным требованиям раздела 4. Проверяются позитивные и негативные сценарии, права доступа, целостность БД, резервное восстановление и формирование отчётности.

Минимальные критерии:
- 100% обязательных `FR-*` реализованы;
- нет открытых дефектов уровня blocker/critical;
- автоматические тесты критичной бизнес-логики пройдены;
- пользователь без права не может выполнить защищённую операцию;
- резервная копия восстанавливается в тестовую БД;
- формируются отчёты:
- оборотно-сальдовая ведомость;
- карточка счёта;
- журнал проводок;
- протокол закрытия периода;

## 7. Требования к подготовке объекта автоматизации

До ввода в эксплуатацию необходимо:
1. подготовить сервер и DNS/TLS;
2. создать БД и сервисную учётную запись;
3. определить пользователей и роли;
4. очистить/нормализовать импортируемые исходные данные;
5. выполнить резервное копирование старого источника;
6. провести обучение пользователей и назначить поддержку.

## 8. Требования к документированию

Комплект поставки должен включать:
- техническое задание;
- описание архитектуры и модели данных;
- инструкцию установки/обновления;
- руководство администратора;
- руководство пользователя;
- описание резервного копирования и восстановления;
- описание API при его наличии;
- программу и методику испытаний/acceptance checklist;
- журнал версий.

Документы хранятся рядом с исходным кодом и версионируются через Git.
